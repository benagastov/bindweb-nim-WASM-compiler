# Libpacks: adding a Nim library

A **libpack** is a plain, uncompressed POSIX ustar `.tar` archive that ships a
Nim library to the browser-based compiler. Packs live in this directory, are
listed in `manifest.json`, and are mounted into the compiler's in-memory
filesystem when the IDE starts.

The important rule:

> You never rebuild `nim.wasm` to add a library. Pack the sources into a tar,
> list the tar in the manifest, refresh the browser.

## The manifest

`libpacks/manifest.json` is generated by `tools/pack-lib.sh` and committed
alongside the tars. It has the following shape:

```json
{
  "version": 1,
  "packs": [
    {"name": "nim-config", "file": "nim-config.tar", "mount": "/nim/config", "strip": 1, "required": false},
    {"name": "bindweb",    "file": "bindweb.tar",    "mount": "/bindweb",    "strip": 1, "required": false}
  ]
}
```

### Top-level fields

| Field     | Type   | Meaning                                          |
| --------- | ------ | ------------------------------------------------ |
| `version` | number | Manifest schema version. Currently always `1`.   |
| `packs`   | array  | Pack entries, in mount order. Must be non-empty. |

### Pack entry fields

| Field      | Type    | Meaning                                                                 |
| ---------- | ------- | ----------------------------------------------------------------------- |
| `name`     | string  | Unique pack identifier. Also the top-level directory inside the tar.    |
| `file`     | string  | Tar filename, relative to `libpacks/`. By convention `<name>.tar`.      |
| `mount`    | string  | Absolute directory in the in-browser filesystem, e.g. `/bindweb`.       |
| `strip`    | integer | Leading path components dropped when extracting (like `tar --strip-components`). Always `1` for packs produced by `tools/pack-lib.sh`, because every tar entry is prefixed with `<name>/`. |
| `required` | boolean | When `true`, the IDE aborts loading if the pack cannot be fetched.      |

### Standard mount points

| Mount         | Contents                                            |
| ------------- | --------------------------------------------------- |
| `/nim/lib`    | Nim standard library (packed when nim.wasm is built) |
| `/nim/config` | `nim.cfg` and friends                                |
| `/bindweb`    | Bindweb framework bindings and C runtime             |
| `/project`    | User code, written by the IDE itself (not a pack)    |

## Adding a library: two commands

```sh
tools/pack-lib.sh mylib path/to/src /mylib
# reload the browser tab
```

That is the whole flow. The tool:

1. copies `path/to/src` into a staging area under a top-level `mylib/` prefix,
2. writes a deterministic ustar archive to `libpacks/mylib.tar` (entries
   sorted by name, ownership zeroed, mtimes fixed, so identical inputs produce
   byte-identical tars),
3. inserts or updates the `mylib` entry in `libpacks/manifest.json`,
   preserving all other packs.

The full argument list is:

```
tools/pack-lib.sh <name> <src-dir> <mount> [required]
```

`required` defaults to `false`; pass `true` only for packs the compiler
genuinely cannot start without (the `nim-stdlib` pack created by the nim build
is the example — both committed packs are optional).

## How the IDE mounts packs

At startup the IDE fetches `libpacks/manifest.json`, then for each pack:

1. fetches `libpacks/<file>` and untars it in memory (`web/src/tar.js`),
2. creates the mount directory (`FS.mkdirTree(mount)`),
3. writes every file at `mount + '/' + name`, after dropping the first `strip`
   path components; entries that strip to nothing are skipped.

A missing `required` pack aborts startup; a missing optional pack is logged
and skipped. Mounting is a pure file-copy into MEMFS — no compilation step is
involved, which is why libraries never trigger a `nim.wasm` rebuild.

## Reproducibility and the staging area

The sources for the committed packs are staged under `libpacks/src/<name>/`
so the tars can be regenerated exactly. To rebuild a pack after editing its
sources, re-run the tool against the staging directory:

```sh
tools/pack-lib.sh nim-config libpacks/src/nim-config /nim/config
tools/pack-lib.sh bindweb    libpacks/src/bindweb    /bindweb
```

`./build.sh libs` does the same for every directory under `libpacks/src/`.

## Current packs

| Pack         | File             | Mount         | Required | Contents |
| ------------ | ---------------- | ------------- | -------- | -------- |
| `nim-config` | `nim-config.tar` | `/nim/config` | no       | `nim.cfg` — comments only. Every cross-compile setting (`--os:linux`, `--cpu:wasm32`, `--mm:arc`, `-d:useMalloc`, `--path`, ...) is passed on the compiler command line by the IDE (SPEC section 5), so nothing needs to live here yet; the compiler also runs fine without this pack. |
| `bindweb`    | `bindweb.tar`    | `/bindweb`    | no       | Bindweb framework: the Nim bindings (`bindweb.nim`, `bindwebtypes.nim`, `bindwebevents.nim`, `bindwebschema.nim`, `panicoverride.nim`) at the pack root so `--path:/bindweb` resolves `import bindweb`; the generated browser-API modules under `apis/` (`dom`, `canvas`, `handles`, `fetch`, `input`, `storage`, `system`, `audio`, `image`, `webgl`, `websocket`, `wgpu`); plus the C runtime (`c/bindweb_runtime.c`, `c/bindweb_runtime.h`). The pipeline reads the runtime from `/bindweb/c/` and compiles it alongside the generated C (SPEC section 6.3). |

### Notes on the bindweb pack

- **Host-side codegen tools are excluded.** `bindwebgenerator.nim`,
  `bindwebjsgen.nim`, `bindwebbuild.nim` and the compiled `bindwebgenerator`
  binary run on the development machine to generate API bindings; they are
  never imported by in-browser user code, so they are not in the pack.
- **`bindweb.nim` ships without its upstream
  `{.compile: "../bindweb_runtime.c".}` pragma.** That relative path cannot
  resolve once the file is mounted at `/bindweb`, and the web pipeline already
  compiles `c/bindweb_runtime.c` itself (SPEC section 6.3 picks exactly one
  mechanism). The legacy IDE bundle applied the same transformation; the
  removal is marked with a comment in the staged file.
- **`apis/` modules are included.** The twelve generated browser-API modules
  (`apis/dom.nim`, `apis/canvas.nim`, `apis/handles.nim`, `apis/fetch.nim`,
  `apis/input.nim`, `apis/storage.nim`, `apis/system.nim`, `apis/audio.nim`,
  `apis/image.nim`, `apis/webgl.nim`, `apis/websocket.nim`, `apis/wgpu.nim`)
  ship in the pack. They were generated from `schema.def` by the host-side
  codegen tool in the reference Bindweb project; `bindwebevents.nim` and user
  programs import them as `apis/...`. To regenerate them, run the generator on
  a desktop Nim install and copy the output into `libpacks/src/bindweb/apis/`,
  then repack.

### How the bindweb staging was produced

The staging tree under `libpacks/src/bindweb/` was assembled from the
reference Bindweb checkout (`Bindweb/src/`):

```sh
REF=/path/to/Bindweb/src
mkdir -p libpacks/src/bindweb/c
cp "$REF"/nim/{bindweb,bindwebtypes,bindwebevents,bindwebschema,panicoverride}.nim \
   libpacks/src/bindweb/
cp "$REF"/bindweb_runtime.{c,h} libpacks/src/bindweb/c/
# then remove the {.compile: "../bindweb_runtime.c".} line from
# libpacks/src/bindweb/bindweb.nim (see the note above)
```

## Conventions for pack contents

- Every entry in a pack tar lives under a top-level `<name>/` directory; the
  manifest's `strip: 1` removes that prefix at mount time, so the tree that
  lands at `mount` mirrors the staging directory.
- Packs are source-only: Nim modules, headers, C sources. Do not pack build
  artifacts, VCS metadata, editor files, or host-side tooling —
  `tools/pack-lib.sh` already strips `.git` and `.DS_Store`.
- Keep file names ASCII and shorter than 100 characters where possible; the
  in-browser untar supports longer names, but short names keep packs
  compatible with the strictest ustar readers.
